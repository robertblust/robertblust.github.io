# The Prose Kit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the sixteen prose pages one source for the CSS they already share, and repair the six drifts that measuring them exposed — one of which is a live bug on companygraph.io's landing page.

**Architecture:** Two new fences, placed at the two regions where the shared CSS is actually contiguous: a **reset** block at the top of every prose page, and a **footer** block near the bottom with two variants, because ten pages carry a credit lockup and six correctly do not. The package holds the reconciled bytes, so the reconciliation and the extraction are the same diff and get reviewed once. Two new checks close holes that let all of this happen unnoticed.

**Tech Stack:** Node 22+, ESM, `node:test` + `node:assert/strict`, zero dependencies. `@robertblust/design` consumed as a git dependency pinned to an exact tag. Playwright for the site suites.

**Spec:** `docs/superpowers/specs/2026-08-30-shared-design-system-design.md`

## Global Constraints

- The package takes **no dependencies and no devDependencies**. Never run `npm install` in it.
- ESM only; `node:test` + `node:assert/strict`; `npm test` must exit 0.
- **No external assets, anywhere.** No font CDN, no remote stylesheet, no linked image.
- A deck must still open from a `file://` URL with no network. This plan touches no deck.
- Sites pin `github:robertblust/design#vX.Y.Z` — an exact **tag**, never a commit SHA. A SHA fails Dependabot's `pinned_ref_looks_like_version?` and the site silently never learns a release happened.
- Stage by name. Never `git add -A` or `git add .`.
- Merge with `gh pr merge --merge`. **Never `--squash`** — GitHub re-authors a squash commit to whoever pressed the button.
- Do not merge any pull request. Open them and stop.
- Never mention closed-source predecessor projects.
- Never print an environment variable's value.
- The git author must be `robert.blust@flatland.ch`. Check `git config user.email` before the first commit in any repository.

## What the measurement found, and where it corrects the spec

The spec says the prose typography kit is **"16 pages; no fence; 54 lines common to all three sites"** and names `.card .cols .lede .note .rules h1` as its content. Both halves need correcting before anything is built on them.

**The 54 lines were measured across the three privacy pages, not across sixteen.** That measurement still holds — 44 of roughly 50 CSS rules are identical on the three privacy pages. But it does not generalise. Counting rules that are byte-identical on **all sixteen** prose pages, after plans 2 and 3 removed the tokens, header and language fences:

| identical on | rules |
| --- | --- |
| 16 pages | **8** |
| 15 | 2 |
| 14 | 2 |
| 13 | 1 |
| 10 | 14 |
| 9 | 9 |
| 1 | 141 |

The lump at 10 is not a coincidence and not drift: it is the **credit lockup**, present on every companygraph.io and guestgraph.io prose page and on none of blust.ch's. Those two sites credit `blust.ch` in their footer; blust.ch is that site and does not credit itself. That is correct, and reconciling it would be vandalism.

The tail of 141 single-page rules is the pages doing their own jobs. `.card`, `.cols` and `.note` — three of the six selectors the spec names — live in that tail. They are a privacy-page pattern, not a sixteen-page kit.

**And the shared CSS is not contiguous.** It appears in two runs with per-page material between them: a reset at the top, immediately after the tokens fence, and a footer block near the bottom. A fence replaces a contiguous region, so this becomes two fences rather than one `prose.css`. That is a departure from the spec's file tree, taken because the alternative — relocating rules on sixteen pages to make one contiguous block — is a large invisible edit whose only purpose is to suit the tool.

### The six drifts

Every one is an unambiguous mistake. None is a page doing something deliberately.

| rule | majority | the exception |
| --- | --- | --- |
| `.mono` | 14 pages define it | **absent on cg:/ and rb:/** |
| `a{color:inherit}` | 15 | absent on cg:/ |
| `body` font stack | 10 | 5 pages add `"Segoe UI"`; cg:/ drops `ui-sans-serif`, `-apple-system` and `-webkit-font-smoothing` |
| `footer` font stack | 14 `"Plex Mono",monospace` | rb:/ and rb:talks/ say `"Plex Mono", ui-monospace, monospace` |
| `.brand svg` | 13 carry `color:var(--c-mid)` — load-bearing on the 10 companygraph.io/guestgraph.io pages whose marks use `stroke="currentColor"`, inert on blust.ch's | rb:/, rb:ideas/, rb:talks/ drop it — also inert; blust.ch's mark fills `.plate`/`.rb` directly and never reads `currentColor` |
| `.brand` | 15 | cg:/ adds `color:var(--ink)` |

Four of the six are on **companygraph.io's landing page**, which reads as though it was written from an older template and never caught up.

**One of them is live.** companygraph.io's landing page contains `class="ctameta mono"` and defines no `.mono` rule, so text the design system marks as data renders in the body sans face in production. `monoScope` cannot catch it: that check asserts mono appears **only** on data, never that data **gets** mono. Task 1 adds the check that can, and proves it fails first.

**One is visible and is not merely tidying: the two `body`/`footer` stack differences change which face a visitor actually gets on a machine lacking the primary.** The `.brand svg` gap is not visible on blust.ch — its mark is `<rect class="plate">` plus `<text class="rb">`, filled directly by `.brand .plate` and `.brand .rb`, and never reads `currentColor` — so missing `color:var(--c-mid)` on three of its six pages changes nothing rendered. It is reconciled to the majority anyway, for the same consistency reason applied to `.mono` and `a{color:inherit}`. If any of these is wanted differently, it is wanted on all sixteen pages, from the package, not on a subset by accident.

### What this plan does not touch

The 141 per-page rules, every deck, the privacy-page pattern (`.card`, `.cols`, `.note`), and `.lede` / `main` / `.title h1` / `h2`, whose variants track landing pages having larger heroes than interior pages. Those are real design differences and the plan leaves them alone.

- [ ] **Step 1: Write the check, in companygraph's `verify/design.mjs`**

Add to `DESIGN_CHECKS`, immediately after `monoScope`:

```js
  // monoScope asserts mono appears only on data. It cannot assert the converse — that an
  // element the design system marks as data actually renders in mono — and the converse is
  // where the bug was: companygraph.io's landing page carried `class="ctameta mono"` and
  // defined no `.mono` rule at all, so the one element on the page marked as a record value
  // rendered in the body sans face, in production, with every check green.
  //
  // Reading the computed style is the point. Asserting the rule text exists in the stylesheet
  // would pass on a page that defines `.mono` after something that overrides it.
  async monoDefined(page) {
    const bad = await page.evaluate(() => {
      const mono = [...document.querySelectorAll(".mono")];
      if (!mono.length) return null;                 // nothing claims to be data: nothing to check
      const fam = (el) => getComputedStyle(el).fontFamily;
      const body = fam(document.body);
      const same = mono.filter((el) => fam(el) === body);
      return same.length
        ? { count: same.length, total: mono.length, family: body }
        : null;
    });
    if (!bad) return null;
    return `${bad.count} of ${bad.total} .mono element(s) render in the body face (${bad.family}) — ` +
           `the .mono rule is missing or overridden`;
  },
```

- [ ] **Step 2: Write the check**

Add to `DESIGN_CHECKS` in `verify/design.mjs`, after `monoDefined`:

```js
  // Discovery drives writing; PAGES drives coverage. `design sync` rewrites the fences it
  // finds, so a page that loses one entirely is invisible to it — and was invisible to
  // everything else too: deleting the header fence from a page left both `design:check` and
  // this suite green. tokenVersion closed that hole for one fence out of four by asserting a
  // marker it happens to look for. This closes it for all of them, from the site's own
  // declaration of what it ships.
  //
  // Fetched raw rather than read from the DOM: a fence is a CSS comment, and comments do not
  // survive into the rendered stylesheet.
  async fences(page, spec) {
    const res = await fetch(spec.absolute);
    const html = await res.text();
    const missing = spec.fences.filter(
      (name) => !new RegExp(`─── ${name} · v\\d+`).test(html) ||
                !new RegExp(`─── end ${name} ───`).test(html));
    return missing.length
      ? `carries no ${missing.map((m) => `\`${m}\``).join(", ")} fence`
      : null;
  },
```

Both halves are checked on purpose: an opening marker with no end is a fence `design sync` will throw on, and an end with no opening is a block nothing owns.

## Rulings taken while writing this plan

Recorded so an executor does not re-open them, and so a reviewer can reject them on sight if they are wrong.

**1. The kit becomes two fences, not the spec's one `prose.css`.** The shared CSS is not contiguous — it appears as a reset at the top and a footer near the bottom, with per-page material between. A fence replaces a contiguous region. The alternative is relocating rules on sixteen pages so the tool has one region to grab, which is a large invisible edit made to suit the tool. *Cost if wrong:* two fences to maintain instead of one, and two entries in every `PAGES` list.

**2. `.card`, `.cols` and `.note` stay per-page**, though the spec names them. They are common to the three privacy pages, not to sixteen. Sharing them means a privacy-page fence, which is a real thing to build and not this plan. *Cost if wrong:* three privacy pages keep 44 duplicated rules until something takes them.

**3. `"Segoe UI"` is dropped rather than adopted.** Ten pages omit it, five carry it, the split follows no site and no page type, and `system-ui` already resolves to it on Windows. *Cost if wrong:* Windows visitors get whatever `system-ui` picks instead of Segoe UI specifically — which is Segoe UI.

**4. The footer takes `"Plex Mono",monospace`, the fourteen-page form.** blust.ch's two pages say `"Plex Mono", ui-monospace, monospace`. Both resolve identically wherever Plex Mono is served. *Cost if wrong:* on a machine where the woff2 fails to load, two pages fall to the OS default rather than to `ui-monospace`.

**5. The `.brand svg` declaration is made consistent on three blust.ch pages by hand — and it is inert there.**
That rule sits outside the header fence deliberately, each site's mark carrying its own colours, so
it cannot move into a shared block without contradicting a decision the header fence documents.

**Corrected after the final review.** This ruling originally said the three pages had *lost the
mark's accent* and that restoring the declaration fixed it. That was false, and the check written to
prove it could not have caught the error. blust.ch's mark is `<rect class="plate">` plus
`<text class="rb">`, filled directly by `.brand .plate` and `.brand .rb`; it consumes no
`currentColor` and has no `stroke`, so `.brand svg{color:…}` changes nothing a visitor sees. Rendered
before and after, `.brand .rb` computes `rgb(127,163,216)` either way. The rule *is* load-bearing on
companygraph.io and guestgraph.io, whose marks use `stroke="currentColor"` three times each — the
"thirteen of sixteen pages carry it" count folded a rule that matters on ten pages together with one
inert on six.

The edit stays, for consistency with the thirteen pages that have it. The claim does not.
*Cost if wrong:* none to rendering, now that the claim matches the code. The cost already paid was a
pull request body asserting a fix that never happened, caught only because the final reviewer
rendered the mark instead of reading the diff.


**6. `monoDefined` returns `null` for a page with no `.mono` element at all.** blust.ch's landing page defines no `.mono` rule and uses no `.mono` element; that is not a bug and the check must not invent one. *Cost if wrong:* a page could add a `.mono` element without the rule and be caught only on the next run — which is the run that would catch it anyway.

**7. Tasks 3-5 commit to the package's `main`, as plans 1-3 did.** It has no reviewers and its gate is `npm test`. *Cost if wrong:* a broken `main` between tasks, bounded because nothing pins an untagged commit.
